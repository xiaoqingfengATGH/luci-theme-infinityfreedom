# 方案 B — 监控台（Console）

## 设计立场

**把首页当成一块仪表盘。** 左侧常驻一列仪表（环形表盘 + 指示灯 + 连接计数），右主区放需要横向空间的内容（流量曲线、设备表、存储表、应用表）。信息密度最高，不做任何折叠。

## 关键取舍

- **布局**：`210px 左轨 + 主列` 的两栏壳。左轨 = 环形表盘（CPU / 内存 / 系统盘 / boot）+ 应用指示灯竖排 + 连接计数；主列 = 流量 → 设备+存储双栏 → 应用表。
- **顶部命令条**：常驻一行紧凑状态（WAN IP、PassWall2、hometunnel、运行时间），sticky 吸顶。
- **环形表盘**：SVG 纯 CSS 实现（`stroke-dasharray`/`stroke-dashoffset`），无 JS 图表库依赖——OpenWrt 上不值得为四个环引入 Chart.js。
- **流量曲线**：`<svg>` + `polyline` 手绘，边框内嵌，零依赖。上下行分列，避免同一坐标系里 3 MiB/s 与 5 KiB/s 差三个数量级导致上行曲线贴底看不清。
- **页面内边距：负**。内容贴边、面板无缝拼接（`gap:1px` 靠背景色描边），是典型 NOC/监控台气质。

## 强项 / 弱项

- **强**：趋势可见（流量曲线）；信息密度高，适合长开在第二个显示器上；指示灯竖排一眼扫全部应用。
- **弱**：实现成本明显更高（环形/曲线/左轨都要自己写）；窄屏需要整体降级为单列；左轨在 1080p 以下会显得拥挤。

## 最适合

愿意把路由面板挂在那儿持续看的进阶使用者，或者装机后要核对一轮完整状态的场景。

## 实现上必须补的一环：流量曲线需要历史

`network.device.status` 只给**累计计数器**（`statistics.rx_bytes` / `tx_bytes`），不是速率。要在前端画出曲线，必须自己在浏览器侧维护一个环形缓冲：

```
每 5s 轮询 → 记录 {t, rx, tx} → 速率 = (cur - prev) / Δt → 推入长度 N 的数组 → 重绘 polyline
```

这只是前端一个几十行的数组，**不需要后端改动**；但页面刷新后曲线即清空（除非写 `sessionStorage`，成本也很低）。方案 A 不涉及这个问题，因为它不画曲线。

## 数据来源

与方案 A 完全一致，额外用到 `network.device.status.statistics.*`（累计字节数，用于算速率）。
