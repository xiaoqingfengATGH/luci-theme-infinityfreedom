# 方案 A — 状态优先（Status-first）

## 设计立场

**先回答问题，再给数据。** 页面第一屏就回答使用者唯一真正关心的那个问题——「路由现在正常吗」——其余信息按重要性向下铺开，原有 OpenWrt 的键值对表格退到最底部折叠起来。

## 关键取舍

- **布局**：单列瀑布流。① 健康横幅 →② 5 张 KPI 卡 →③ 网络接入 + WAN 双栏 →④ 关键应用 →⑤ 存储 →⑥ 折叠的系统详情。
- **五张 KPI 同一解剖**：每张卡都是「标题 / 大值 / 副行 / 底部状态脚注」。比例型（CPU、内存、系统盘）用 4px 轨道表达比例，状态型（WAN、接入设备）用**小圆点 + 文字脚注**，刻意不给轨道——避免「满格绿条」被误读成 100%。
- **色彩**：绿=健康/在线，蓝=信息，橙=警告，红=停止，灰=禁用/只读。KPI 大值超阈值自动转橙/红。
- **关键应用用卡片网格而非表格**：状态色做左边框（3px），图标按钮就在行内，一眼扫完 8 个应用的开关状态。
- **存储**：只读固件镜像 `/rom` 用斜纹中性轨 + 「只读」标签，不用 100% 满格进度条——OpenWrt 上 `/rom` 恒 100% 是构造使然，画成满格会在每次进页面时误报。
- **折叠**：型号/固件/内核/时间等原有字段收进 `<details>`，默认收起，需要时才展开。

## 强项 / 弱项

- **强**：扫描速度最快，一眼定论；不需要横向滚动；移动端退化最自然；实现成本最低（纯 CSS + 少量 DOM 重组）。
- **弱**：没有实时曲线，看不到「趋势」；不适合盯着看流量波动的运维场景。

## 最适合

日常「看一眼就走」的使用者——也就是你描述的主要场景：路由正常吗、有多少设备、盘满没满、关键应用活着没。

## 数据来源（已在 247 实测）

| 区块 | 来源 |
|---|---|
| CPU% / 负载 | `luci.getCPUUsage` / `system.info` |
| 内存 | `system.info.memory` |
| WAN 状态 / IP / 网关 / 租约 | `network.interface.dump` → `wan`（含 `uptime`、`ipv4-address`、`route[].nexthop`、`dns-server`、`data.hostname`） |
| 接入设备 | `luci-rpc.getDHCPLeases` + `luci-rpc.getHostHints` 合并 |
| 存储 | `luci.homestatus.status` → `disks`（已有） |
| 关键应用 | `luci.homestatus.status` → `apps`（已有） |
| 活动连接数 | `luci.getConntrackList` |

> **注意**：247 上 LAN 侧 dnsmasq 未发放任何租约（实测 0 条），所以「接入设备」目前只能由 ARP/邻居表 + 接口地址推导。典型家用部署（LAN 开 DHCP）是以租约为主、ARP 补充。设计上已按「租约优先、ARP 兜底」处理，并显式标注空态。
